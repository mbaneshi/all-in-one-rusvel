- [`docs/status/current-state.md`](../status/current-state.md) §4: *"Seven 'business' engines — Finance, Product, Growth, Distro, Legal, Support, Infra are thinner than the 6 wired engines (Forge/Code/Content/Harvest/Flow/GTM)."*

Even where engine logic exists, **AI agents cannot reach 10 of 13 engines through tools**. The chat in those departments is decoration over an unreachable backend. This single fact is the largest gap between "Virtual Agency" pitch and shipped reality.

## 5. Inventory — autonomy

The "Virtual Agency" pitch claims autonomy. Reality is **SEMI** at best:

| Component | Mode | Notes |
|---|---|---|
| Job queue worker | SEMI | Polls every 100ms; executes jobs *queued by humans/crons/events* — never enqueues its own follow-up work |
| Cron scheduler | AUTONOMOUS infra, **MANUAL setup** | 30s tick loop runs; **zero schedules ship by default** — nothing fires unless a user registers one |
| Webhooks → flows | AUTONOMOUS infra, **MANUAL setup** | Inbound HMAC-validated, emits event; downstream requires hand-written `EventTrigger`; no UI to register |
| Approval gates (ADR-008) | MANUAL | Blocks ProposalDraft + OutreachSend until human approves; no timeout, no escalation, no auto-approval policy |
| Forge mission pipeline | SEMI | Orchestrates scan→score→propose→draft when explicitly enqueued via custom `forge.pipeline` job |
| Flow execution | MANUAL | Runs only on `POST /api/flows/{id}/run` (or via an EventTrigger that's been hand-registered) |
| Goal-condition loop | ABSENT | Forge generates missions but never *executes* them or reschedules based on progress |

Also missing per [`docs/state-report/07-metrics-and-gaps.md`](../state-report/07-metrics-and-gaps.md) Priority 2: *"Job queue persistence — currently `Vec<Job>` behind Mutex — volatile. Jobs are lost on restart."* This means even partial autonomy doesn't survive a binary restart.

Additional missing primitives per [`docs/status/gap-analysis.md`](../status/gap-analysis.md) HIGH PRIORITY:

- **Loop Detector** — *missing.* Without it, agent loops can run forever.
- **Context Pruner** — *missing.* Token budgets overflow without truncation.
- **Rate Limiter** — *missing.* No protection against API quota exhaustion.
- **Best-of-N Runner**, **Strategy Set** — *missing.* Old `forge-agent` had 3 strategies (minimal_changes, modular_refactor, thorough_with_tests); RUSVEL has none.
- **112 personas in 11 divisions** (old) vs **10 hardcoded** (RUSVEL).

These five items make the difference between "an agent runtime" and "an agent runtime you can actually leave unattended."

## 7. Research — what separates production agents from demos

Drawn from the LangChain 2025 survey and the AWS/MIT references above. Seven signals separate "we deployed it" from "we trust it":

1. **Durable execution with per-step checkpointing** — replay any run from any step.
2. **Replayable, inspectable runs** — view every tool call and LLM turn for any historical run.
3. **Goal-condition loops, not just task queues** — a goal with an explicit success condition checked on a cycle.
4. **Structured evals** — only 52% of teams do this; biggest separator between deployed and trusted.
5. **Sandboxing** — every tool action runs isolated. Suna uses Docker; OpenHands has its own.
6. **Per-run secrets vault** — credentials are scoped, audited, revocable; not env vars.
7. **HITL that surfaces as a workflow** — approvals with visibility, timeout, escalation.

RUSVEL has #7 partially (approval gates exist; UI is weak; no timeout). The other six are absent or partial.

## 8. Where RUSVEL can credibly win

Four defensible niches given the constraints:

1. **Local-first single binary.** Drop one binary on laptop or VPS. No Docker, Supabase, Redis, Postgres. Real moat for privacy-conscious and air-gapped use cases. No competitor in this lane.
2. **BYO-LLM with 4 providers in one binary.** Ollama + OpenAI + Claude API + Claude CLI. No competitor ships all four together.
3. **Code-aware agency for developer-founders.** The `code-engine` (BM25 + symbol graph) + `forge-engine` combination can ground every agent action in actual codebase state. No "agency" product has this.
4. **Deterministic, auditable runs.** SQLite WAL gives an append-only record. With per-step checkpointing (currently missing), RUSVEL could offer "replay any run from any step" as a first-class feature.

## 9. Direction options (decision pending)

Five sharp moves, ranked by leverage. **Not committed — these are options to choose from.**

### Option A — Cut the seven skeleton engines

**What:** Delete `finance-engine`, `product-engine`, `growth-engine`, `distro-engine`, `legal-engine`, `support-engine`, `infra-engine`, plus their `dept-*` wrappers, API routes, and frontend pages. Replace with one `dept-plugin` crate: JSON-Schema-described runtime plugins users can register without recompiling.

**Why now:** [`docs/status/current-state.md`](../status/current-state.md) §4 already concedes these are thin. [`docs/state-report/03-engines-and-departments.md`](../state-report/03-engines-and-departments.md) confirms agents can't even invoke them. Maintaining 7 fake engines costs more than it earns.

**Cost:** ~7 crates × ~1,600 LOC + corresponding `dept-*` + frontend pages. Estimate 2–3 days to delete cleanly.

**Risk:** Loss of "14 departments" marketing number. Mitigation: pitch becomes "5 deep engines + extensible plugin SDK."

### Option B — Add run-level checkpointing in rusvel-jobs

**What:** Every job step writes input/output/state to a `job_checkpoints` table in SQLite. Unlocks replay, time-travel debug, retry-from-step.

**Why:** Cited as the single biggest production-vs-demo separator. Also fixes the volatile-jobs bug already filed in [`docs/state-report/07-metrics-and-gaps.md`](../state-report/07-metrics-and-gaps.md) Priority 2.

**Cost:** ~300 LOC in `rusvel-jobs` + migration + opt-in hook in agent loop. Estimate 3–5 days.

**Risk:** Storage growth — needs a retention policy.

### Option C — Ship one killer demo: nightly harvest goal loop

**What:** Cron → `HarvestEngine::scan` → LLM score → top 3 as approval-gated proposals → Telegram notification. Ship as `RUSVEL_DEMO=harvest` one-command preset.

**Why:** Exercises every real adapter end-to-end (cron, jobs, LLM scoring, CDP browser, approval gate, outbound notify). Converts the pitch from "tool with departments" to "thing that does work while you sleep."

**Cost:** ~1–2 days of glue code; everything underneath exists.

**Risk:** None significant.

### Option D — Fix Ollama + OpenAI streaming

**What:** Replace batch-fallback in `ollama.rs` and `openai.rs` with real SSE streaming. Both providers expose streaming APIs.

**Why:** Eliminates a visible credibility gap on every demo. Two of four advertised providers don't actually stream.

**Cost:** 2–3 days.

**Risk:** Minor — both providers are well-documented.

### Option E — Add a `rusvel-evals` crate

**What:** Fixture-based eval suite that runs forge + harvest pipelines and asserts on output shape and score distribution. No new frontend.

**Why:** Only 52% of agent teams have evals; it's the artifact that turns "demo" into "trust." Becomes the merge gate for engine work.

**Cost:** 3–5 days for scaffold + first 5 fixture cases.

**Risk:** Fixture maintenance overhead.

### Suggested ordering (if all five chosen)

C → D → B → A → E.
Killer demo first to validate the loop. Streaming fix next to make the demo presentable. Checkpointing third because it backstops everything else. Cuts fourth because they require none of the above. Evals last because they need stable surfaces to test against.

## 10. What this audit deliberately did **not** decide

- Whether to **pivot the pitch** ("Virtual Agency" → "Local-first agent runtime for developer-founders").
- Whether to **embrace MCP-first** and pivot `dept-*` to be MCP servers consumable by Goose / Claude Desktop / Cursor.
- Whether to **drop the frontend** entirely and lean on MCP + CLI + TUI.
- Whether to keep four LLM providers or focus on the two that actually stream.

These are larger questions to bring up after Options A–E are chosen or rejected.

## The arc, in one paragraph

The session started with a strategic question — "is RUSVEL still worth building, given
Anthropic ships orchestration daily?" — and ended with real, tested, committed code. In
between: research surfaced that the underlying idea (AI drafts, human approves) had been
independently rebuilt at least four times across the user's own history, plus industry-wide
(GitHub's `company-os` topic, xAI's Grok Bot). That led to locking RUSVEL's role as an
estate-wide coordination layer rather than a competing agent-orchestration platform, then to
concretely building that role — starting with one real venture (`mbaneshi.ir`) rather than
generalizing in the abstract first.

## What's true right now

**Locked decision** (`ledger.jsonl`, `d-001`, commit `630751d`): RUSVEL is the estate's
ports-and-adapters coordination layer — narrow in what it executes, broad in where it
reaches. It doesn't rebuild agent orchestration (Claude Code/Cowork already do that) or the
tenant/capability execution substrate (`capability-tenant-infra` already does that); its job
is coordinating across both, plus a deterministic, auditable core.

## Things worth knowing that aren't obvious from the code

- **AvalAI is an Iran-market LLM/media aggregator** (`api.avalai.ir`), OpenAI-compatible for
  text and images, genuinely async for video (billing starts on request-accept; a dropped
  connection must be re-polled, never re-created — see `AvalAiMediaGen::generate_video`'s
  doc comment). The mbaneshi.ir key lives in `.envrc` (gitignored) as `OPENAI_API_KEY` /
  `OPENAI_BASE_URL` — that's deliberate, not a naming mismatch: RUSVEL's existing
  OpenAI-compatible-gateway support just works.
- **`~/aval-ai`'s own `d-001`** ("AvalAI as `capability-tenant-infra`'s `ai_engine`
  capability") is deliberately left `proposed`, not adopted or rejected — cross-referenced
  from RUSVEL's own decision, not silently ignored. Revisit only if a second real consumer
  needs AvalAI execution to live inside CTI rather than RUSVEL.
- **`mbaneshi-ir-site`'s RFC-0001** (mbaneshi-ir-site#12, its own repo) is still `proposed`,
  unratified — not RUSVEL's to resolve. If it ever ratifies, its `agents` capability
  (reception/booking/triage on the live site) and RUSVEL's content pipeline (blog/build-in-
  public, git-committed) are different surfaces by design, not expected to collide.
- **`content-factory`'s `mbaneshi` pack** (a different repo, `packs/mbaneshi/`, commit
  `82eb049`) was built as a candidate draft+render engine, then explicitly superseded by
  direct user correction — real brand data, reference material, not load-bearing. Don't
  build on it; the tenant axis lives natively in RUSVEL now.
- **Video generation has not been run against the real API.** Cost/duration are unconfirmed
  (AvalAI's catalog had no pricing populated for video models at design time). Get an
  explicit go-ahead before spending on it — same discipline the image-generation test used.
- **`gtm-engine` and `harvest-engine` have no tenant awareness.** Only `content-engine` does.
